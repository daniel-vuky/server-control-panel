# server-control-panel

## Task board

Work is tracked on the GitHub Project board: https://github.com/users/daniel-vuky/projects/2 (project `2`, owner `daniel-vuky`).

Columns (the `Status` field): **Backlog → Ready → In progress → In review → Done**.

- Only pick up issues in **Ready**. Backlog items are not specified enough yet.
- One flow = one branch = one PR. A flow is a group of dependent issues worked end to end in one round (a single issue is a flow of one). Branches: `feat/<first-issue>-<slug>` or `fix/<first-issue>-<slug>`.
- PR bodies start with one `Closes #<issue>` line per issue in the flow, so merging once closes them all.
- Claude moves cards to In progress and In review; the user reviews and merges. Never merge PRs yourself.

Skills for the board:

- `work-board-item` — pick the next Ready issue and work it end to end, add an issue to the board, or move a card. Holds the project/field/option IDs.
- `get-board-items` — read and filter board items.
- `create-issues` — file new issues using `.github/ISSUE_TEMPLATE/` (feature, bug). After creating one, add it to the board with `work-board-item add <N>`.
- `update-issues` — edit issue fields or comment.

`gh` must be logged in as `daniel-vuky` with the `project` scope (`gh auth status`).

## Commands

The host needs only Docker and `make`; Go, Node, pnpm and every tool run in the dev image (ADR 0009). Run them through `make`, never natively.

- `make dev` (the default): start Air (Go hot reload) and Vite (web hot reload). UI at `http://localhost:5173`, API on `127.0.0.1:8471` inside the dev container, with the dev identity `dev@localhost` (build tag `dev`). The api container gets the host's Docker socket (root-equivalent on the host), `WORKSPACE_ROOTS=/src/dev/workspaces` and `PANEL_DATA_DIR=/src/data` (gitignored).
- `make fixtures-up` / `make fixtures-down`: start and remove the sample compose projects in `dev/workspaces/` with the host's Docker (`shop` Partial, `notes` Running, `blog` stopped), so a dev scan shows several statuses. `make test` and CI never need Docker.
- `make shell`: open a bash shell in the dev image.
- `make setup`: install web dependencies (frozen lockfile) into the `node_modules` volume.
- `make dev-image`: build the dev toolchain image (cached). `SKIP_DEV_IMAGE=1` reuses a prebuilt `scp-dev` image (CI does this).
- `make test`: Go tests (release and `dev` tags), then web tests.
- `make lint`: golangci-lint, Biome (warnings fail), the TypeScript typecheck and shellcheck on the deploy scripts.
- `make fmt`: format Go and web sources.
- `make typegen`: regenerate `web/src/api/types.gen.ts` from the Go types in `internal/api` (`tygo.yaml`).
- `make build`: build the web app, then the single release binary at `bin/panel` (`VERSION` defaults to the short git SHA, or `dev` when git is unavailable).
- `make image`: build the production image `scp-panel:local` with the host's Docker (needs BuildKit).
- `make deploy-test`: run the deploy script tests and render the compose project with `docker compose config`, in a Linux container.
- `make deploy-e2e`: install, update and uninstall end to end in a throwaway `docker:29-dind` with a local registry (manual, needs privileged containers; not in CI).
- `make ci`: lint, test, build, then check that `types.gen.ts` is committed. `.github/workflows/ci.yml` runs it on pull requests, then also runs `make deploy-test` and builds the production image.

Production deployment is built (ADR 0008). `deploy/` holds the compose project, `install.sh`, `uninstall.sh` and the `updater.sh` loop; `.github/workflows/release.yml` pushes `latest` and `sha-<short>` images to GHCR after CI passes on `main` (docs-only pushes do not release). The panel service has `mem_limit: 384m` (up to 3 live log follows of about 50 MB each; ADR 0008 note). The owner's guide is `docs/deploy.md`.

## Architecture

One Go binary (`cmd/panel`) serves the JSON API and the embedded React app (`web/`, built into `internal/web/dist`). It binds `127.0.0.1` only and is reached through a Cloudflare Tunnel (ADR 0006).

- `internal/config`: reads `PANEL_ADDR` and refuses any address that is not `127.0.0.1:<port>`. It also reads `WORKSPACE_ROOTS` (comma-separated absolute paths, the only folders that may become workspaces) and `PANEL_DATA_DIR` (the panel's own state, default `/data`).
- `internal/auth`: the `Verifier` seam and the `Require` middleware. Release builds use `AccessVerifier`: it checks the `Cf-Access-Jwt-Assertion` JWT (signature, issuer, audience, expiry) and needs `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`, or startup fails. Setup is in `docs/cloudflare-access.md`. The `dev` build tag swaps in the fixed `dev@localhost` identity; it must never reach a release binary.
- `internal/api`: the router and API types. Only `GET /api/health` is public; everything else goes through `auth.Require`. `GET /api/me` returns the verified email. Workspace flow: `POST /api/scans` (starts a scan, 409 while one runs), `GET /api/scans/{id}`, `GET /api/scans/{id}/events` (per-job SSE: `progress`, then `end`), `POST /api/scans/{id}/track` (stores the workspace and its projects, tracked or ignored, in one transaction), `GET /api/workspaces`, `GET /api/projects` (tracked projects with effective status and allowed `actions`; Unknown when Docker cannot be read). Lifecycle and live state: `POST /api/projects/{id}/{action}` (`start`, `stop`, `restart`; waits for the outcome and answers 200 `ActionResult {outcome, status, message, actions}`; 409 `locked` or `not_allowed` and 503 `docker_down` with `ActionRefused`; 404 for an unknown project), `GET /api/events` (SSE, one `state` event per change, a `LiveState {dockerUp, projects}`) and `POST /api/docker/check` (Retry: one fresh Docker read for the hub). Every state-changing `POST /api/*` must send `Content-Type: application/json` or it gets 415 and nothing runs (`requireJSON`, inside `auth.Require`). Field errors are 422 `{error, field, code}`.
  Workspace management: `POST /api/rescans {workspaceId}` (0 = every workspace; answers 202 `{id}`, 409 `ScanBusy` while a scan runs, 409 with no workspace, 404 for an unknown `workspaceId`), `POST /api/workspaces/{id}/remove` (deletes the workspace and its projects, 200 `{removed}`; 409 while a scan runs or a project is locked or in flight; 404 for an unknown workspace; records `workspace.remove` on every answer after the workspace is found, except a 404 from a concurrent removal) and `POST /api/projects/{id}/untrack` (a present project becomes ignored, a Not found one is deleted; 200 `{removed}`; 409 `ActionRefused` while locked; 404 unknown). `POST /api/scans/{id}/track` also takes a rescan job: it lists only the rows to add, adds them to the existing workspaces (an ignored one is tracked again) and stores the New rows it leaves out as ignored. `ScanJob` and `ScanBusy` carry `rescan` (and `ScanJob.workspaceIds`), `Project` carries `missingSince`.
  Project detail: `Project` also carries `publicDomain`, `stopTemplate` (`stop` or `down`), `alertCpuPercent` and `alertRamMb` (null = server default), `composeFiles`, the live `cpuPercent`, `memBytes` and `upSince`, and `containers` (`Container`: status word, ports, per-container CPU and RAM, restart count, `startedAt`, `exitReason`, `health`; a Not created row per service without a container). `GET /api/projects` reads only `docker ps`, so there the metrics are null and `upSince` is empty; `/api/events` fills them in. `POST /api/projects/{id}/settings` replaces display name, public domain, stop template and both alert thresholds in one call (200 with the `Project`; 422 field errors; 404 unknown; the panel's own project cannot change its template). `GET /api/projects/{id}/logs?service=` is SSE: `lines` events (the first is the backlog) and a final `end {reason, message}`; only an unknown id is a plain 404, every other refusal (`unknown_service`, `not_found`, `docker_down`, `too_many_log_streams`) is an `end` reason because `EventSource` cannot read a non-200 body. After an untrack, a removal or an add the API calls `Hub.Refresh()`.
- `internal/runner`: the only package that runs processes. A registry of argv templates keyed by (action, stack): `compose.config`, `compose.up`, `compose.stop`, `compose.restart`, `compose.down`, `compose.logs` (follow, all services), `compose.logs.service` (follow, one service) and `compose.logs.tail` / `compose.logs.tail.service` (the 500-line backlog; each with a `.override` variant), plus `docker.containers`, `docker.inspect`, `docker.stats` and `docker.ping`. Placeholders have kinds: a path (absolute, clean), `ids` (1 to 1,000 full 64-hex container ids, one argv element each), `service` (`^[A-Za-z0-9][A-Za-z0-9_.-]{0,62}$`, so never a flag) and `since` (RFC 3339 UTC). Read commands time out after 15 s, lifecycle commands (`compose.up/stop/restart/down`) after 60 s, `docker.ping` after 5 s; each output stream is capped at 4 MiB. `Runner.Stream` is the one call with no timeout: it delivers each masked stdout/stderr line (cut at 16 KiB) until the command exits or its context is cancelled, and it runs only the follow actions, which `Run` refuses (ADR 0010). Every command runs in its own process group and the whole group is SIGKILLed on timeout or cancel, so a `docker compose` plugin child cannot outlive it; the panel containers run with `init: true` to reap the killed trees. Stderr and error messages are masked (`••••`) for the secret values the caller passes. The child gets a minimal environment (`PATH`, `HOME` and `DOCKER_CONFIG` under `$PANEL_DATA_DIR/docker`), never the panel's own.
- `internal/roots`: the `WORKSPACE_ROOTS` guard. Resolves a path (symlinks, `..`) to one canonical form and refuses anything outside the roots, with the error codes `not_absolute`, `not_found`, `unreadable`, `outside_roots`, `not_a_folder`.
- `internal/store`: SQLite at `$PANEL_DATA_DIR/panel.db` (`modernc.org/sqlite`, no cgo), with embedded migrations applied on open. Holds workspaces, projects and scan jobs; a job left running becomes interrupted on reopen. The `activity` table (migration 0002) is the append-only record of who did what: two inserts (a `running` row, or a finished one such as a refusal), one guarded `running` to final update and a store-level reader `RecentActivity` (no HTTP route yet), never a delete; the actor email comes only from `auth.FromContext`, the reason is masked, and a row left `running` becomes `interrupted` on reopen. Scans, tracks and project actions (refusals included) are recorded. Migration 0003 adds `projects.missing_since` (set when a rescan cannot find a tracked project's folder, cleared when it is found again; NULL means present). Workspace management lives in `internal/store/manage.go`: `RemoveWorkspace`; `UntrackProject` (a tracked project becomes ignored and its databases are deleted; a missing one is deleted); `ApplyRescan` (a refresh clears missing; Found matches by path in any workspace, Missing is scoped to the reporting workspace; only `state='tracked'` rows; `display_name` is never touched); `AddProjects` (adds into existing workspaces, re-tracks ignored rows, writes a "tracked" marker into the job params in the same transaction; `ErrAlreadyTracked`, `ErrAddedMeanwhile`, `ErrWorkspaceGone`). The activity actions are now `scan.start`, `scan.track`, `workspace.rescan`, `workspace.remove`, `project.start|stop|restart`, `project.untrack`, `project.remove` and `project.settings` (email, changed fields with old and new values). Migration 0004 adds `projects.public_domain`, `stop_template` (`stop` default or `down`, CHECKed) and the nullable `alert_cpu_percent` and `alert_ram_mb`; scans and rescans never touch them. `UpdateSettings` (`internal/store/settings.go`) replaces all five settings in one transaction and returns the project before and after.
- `internal/project`: the `Status` values (`running`, `partial`, `stopped`, `error`, `unknown`, plus the in-between `starting`, `stopping`, `restarting` and `notfound`) and the mapping from `docker.containers` output. `Allowed` gives the actions a status permits (the server uses it; the UI reads the `actions` the server sends and never derives them), and `AnyActive` says whether anything runs or restarts. The actions `untrack` (offered in every status except in flight and Not found, even with Docker down and for the panel's own project) and `remove` (the only action of `notfound`) are only ever stored as the project's allowed actions; both are served by `POST /api/projects/{id}/untrack`.
- `internal/control`: project lifecycle. The `Controller` holds per-project in-memory locks; `Do` checks (not allowed, locked, Docker down, the panel's own project; a refusal is a `*Refusal` error, answered 409 or 503 and recorded in `activity` as `refused`), runs the command with the project's `.env` secrets masked, re-reads Docker and settles an `Outcome` (`ok`, `failed`, `timed_out`). A start or restart that exits 0 but leaves anything but Running or Partial is failed (Partial counts as started); a stop that exits 0 but leaves something running or restarting is failed. The command runs on its own context, so a client disconnect never aborts it, and the lock is released on every path. The `Hub` does one non-overlapping Docker read every 5 s, shared by all `/api/events` subscribers and only while someone is subscribed; a generation counter drops a stale read that lands after a lock change, and `Check` backs Retry. Lock order: `hub.mu` then `ctl.mu`. `Views` decides a row in this order: in flight, then a missing project as `notfound`, then Docker; a project held for a store write keeps that computed status but has no actions. `Do` re-verifies the project after taking the lock, so no command runs on a project untracked meanwhile. `Untrack` holds the project's lock for the store write and records `project.untrack` (or `project.remove` for a missing project). `WithLocks` holds several projects' locks for a write (used by workspace removal); it does not publish on a successful release, so the caller calls `Hub.Refresh`. The tick runs `docker.inspect` (restart count, start time, health, exit reason) for the tracked, present projects' containers right after `docker ps`, and a separate non-overlapping metrics read (`docker.stats`) runs every 10 s while someone subscribes; failed metrics reads keep the last values for 30 s, then they go null. Inspect and metrics are maps keyed by container id and survive `lockChanged`. `Hub.Containers(ctx)` is `Check` plus the container list (ok false when Docker is down) for the log streams. A stop on a project with the `down` template runs `compose.down` (containers and networks removed, volumes kept; it then reads Stopped), and the panel's own project always stops with `stop`. `Hub.Refresh` asks for a fresh read and always bumps `tsGen` (so a tick that read the store earlier publishes nothing); then, with no loop running it invalidates the cache, with a tick running it does nothing more (that tick drops its list and ticks again), otherwise it starts a detached tick.
- `internal/scan`: the workspace scanner. It walks depth 1-3 (symlinks, hidden folders and `node_modules` skipped; no descent into a project), reads each compose file with `docker compose config --format json --no-env-resolution` through the runner, parses `.env` for masking and database hints, detects databases without keeping any secret, and recognises the panel's own project (Monitor only) by its image label. It runs one scan at a time and fans progress out through a broadcaster. A rescan is a `scan` job with params `{"depth":0,"rescan":[workspace ids]}`; each workspace is scanned at its own depth, and the `Guard` (set with `SetGuard`, the `WORKSPACE_ROOTS` check) is run by the Manager. A workspace is skipped with a warning when the Guard refuses it or it resolves to a different canonical path, when its root is missing or unreadable, or when it lists no compose folder while it has tracked projects: nothing is marked missing and its `last_scan_at` is kept. A project refreshes only from what was read (config and containers), so a failed `compose config` keeps the stored services and Docker down keeps the panel's own `self` flag. A new path under two nested workspaces belongs to the deepest scanned root. `OnChange` calls `Hub.Refresh` after the apply, and `WhileIdle(fn)` runs `fn` only while no scan runs (workspace removal uses it).
- `internal/logs`: live container logs for `GET /api/projects/{id}/logs`. One shared stream per (project, service or all): the first viewer runs the backlog (`compose logs --tail 500`, through `Run`), sorts it by timestamp, then starts one `--follow --since <start>` through `Runner.Stream` only if a container of the selection is running or restarting (else it sends the backlog and ends `exited`); follow lines already in the backlog are dropped, so the hand-off has no gap or duplicate. Lines are parsed (ANSI stripped, compose status lines dropped, the prefix mapped to a container through `Hub.Containers`) and masked with the project's `.env` values. A stream keeps a 500-line ring for late viewers, sends batches at most every 200 ms, ends a viewer that falls 16 batches behind (`slow`) and cancels its follow process the moment the last viewer leaves. At most 3 follows run panel-wide (a joiner of an existing stream always gets in); a fourth is refused as `too_many_log_streams`. Reading logs is not recorded in `activity`.
- `deploy/`: the shell scripts and `compose.yaml` that install, update and uninstall the panel on a server, with their tests in `deploy/test/`. Run on Linux only; test them through `make deploy-test`.
- `internal/web`: serves the embedded single-page app for every non-API path.
- `web/`: React, Vite and TypeScript. Pages are declared in `web/src/app/routes.ts`. Built: `/onboarding` (path and depth, live scan progress, results table, Add), the `/` Dashboard table of tracked projects with lifecycle controls, and the Workspaces card on `/settings`. The app runs in a data router (`createBrowserRouter`, `routeObjects` in `web/src/app/App.tsx`, so a page can block navigation). `LiveProvider` (`web/src/app/live.tsx`) wraps the shell (`AppShell`) and holds one `EventSource` on `/api/events` for every page; it shows the Docker banner (Retry posts `/api/docker/check`) and the connection state: `ConnectionBadge` (top right of the content area) reads Realtime, "Connection lost, retrying…" (the page dims to 55 %) or, when `/api/me` shows the Access session ended, "Session expired" with Reload. `StatusBadge` is the status pill for all nine statuses. The Dashboard row has a Start/Stop switch and a ⋯ menu (Start, Restart); Stop and Restart of a Running or Partial project ask first in a confirm dialog; results show in a toast stack. The row's allowed actions come from the server, never re-derived in the browser. The project name links to `/projects/:id`, and the table has live CPU and RAM columns. `web/src/lib/useProjectActions.tsx` holds the action flow (confirm, run, toast) shared by the Dashboard and the detail header. `/` redirects to `/onboarding` when there is no workspace (first-screen rule; #26 setup steps are not built). The Dashboard header has a Rescan button; a Not found row shows "Folder missing since the <HH:MM> scan. Not removed automatically." and its ⋯ menu offers Stop tracking (ask first, toast "Stopped tracking <name>") or, for a Not found row, Remove from list. Both are red, per #72, which is a recorded drift from design 10's neutral Remove button. `/rescan/:id` (`RescanPage`, `RescanResults`) shows live rescan progress, then the New rows (tagged New), a "Show ignored (N)" toggle where an ignored project can be checked and tracked again, and warnings that stay; a rescan with nothing new ends "Rescan finished: no new projects, Y not found". `/onboarding` also accepts router state `{scanId}` to attach to a running first scan, and `/rescan/:id` on a first-scan job redirects there. The Settings Workspaces card has Rescan and Remove per workspace; `web/src/lib/useRescan.ts` is the shared start-or-attach hook for the Dashboard and Settings. `/projects/:id` (`ProjectPage` with `projectContext`) is the detail page: header (name, status, containers, path, domain, uptime, actions) and four tab routes that live in the URL: Overview (index: CPU/RAM, containers table, a failed-components panel whose View logs opens Logs on that container's most recent error), `/logs` (`ProjectLogs`, `useLogStream`: service filter, level words, 2,000 lines held, Download, reopens when a container runs again), `/database` (detected databases, read only; backups are not set up yet) and `/settings` (`ProjectSettings`: name, public domain, stop template, alert thresholds stored but not sent, Stop tracking; unsaved changes ask before navigating away). The other pages are placeholders for later issues.
- Only `internal/runner` may import `os/exec` (depguard in `.golangci.yml`, ADR 0005). It runs whitelisted `docker` commands without a shell; there is no terminal or free-form command anywhere.
- `dev/workspaces/`: sample compose projects used as the dev `WORKSPACE_ROOTS` (`shop`, `blog`, `notes`, `clients/acme/web`, `broken`, `tools`, and an `outside` symlink that must be skipped). `shop/.env` holds `devpassword`, which must never appear in the DB, logs or API.
- v1 manages docker compose projects only.

Decisions live in `docs/decisions/` (ADRs 0001-0010). The product spec and design references are in `knowledge/`.

## Conventions

- After changing types in `internal/api`, run `make typegen` and commit `web/src/api/types.gen.ts`; `make ci` fails if it is stale.
- Run Go, pnpm and lint tools through `make`, not natively on the host.
- `docs/superpowers/` (local design and plan docs) is gitignored; keep it local and do not commit it.
