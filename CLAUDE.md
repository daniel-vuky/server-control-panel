Columns (the `Status` field): **Backlog → Ready → In progress → In review → Done**.

`gh` must be logged in as `daniel-vuky` with the `project` scope (`gh auth status`).

## Commands

The host needs only Docker and `make`; Go, Node, pnpm and every tool run in the dev image (ADR 0009). Run them through `make`, never natively.

- `make dev` (the default): start Air (Go hot reload) and Vite (web hot reload). UI at `http://localhost:5173`, API on `127.0.0.1:8471` inside the dev container, with the dev identity `dev@localhost` (build tag `dev`). The api container gets the host's Docker socket (root-equivalent on the host), `WORKSPACE_ROOTS=/src/dev/workspaces` and `PANEL_DATA_DIR=/src/data` (gitignored).
- `make fixtures-up` / `make fixtures-down`: start and remove the sample compose projects in `dev/workspaces/` with the host's Docker (`shop` Partial, `notes` Running, `ledger` Running with a PostgreSQL and a MariaDB for backups, `blog` stopped), so a dev scan shows several statuses. `make test` and CI never need Docker.
- `make shell`: open a bash shell in the dev image.
- `make setup`: install web dependencies (frozen lockfile) into the `node_modules` volume.
- `make dev-image`: build the dev toolchain image (cached). `SKIP_DEV_IMAGE=1` reuses a prebuilt `scp-dev` image (CI does this).
- `make test`: Go tests (release and `dev` tags), then web tests.
- `make lint`: golangci-lint, Biome (warnings fail), the TypeScript typecheck and shellcheck on the deploy scripts.
- `make fmt`: format Go and web sources.
- `make typegen`: regenerate `web/src/api/types.gen.ts` from the Go types in `internal/api` (`tygo.yaml`).
- `make build`: build the web app, then the single release binary at `bin/panel` (`VERSION` defaults to the short git SHA, or `dev` when git is unavailable).
- `make image`: build the production image `scp-panel:local` with the host's Docker (needs BuildKit).
- `make deploy-test`: run the deploy script tests and render the compose project with `docker compose config`, in a Linux container.
- `make deploy-e2e`: install, update and uninstall end to end in a throwaway `docker:29-dind` with a local registry (manual, needs privileged containers; not in CI).
- `make ci`: lint, test, build, then check that `types.gen.ts` is committed. `.github/workflows/ci.yml` runs it on pull requests, then also runs `make deploy-test` and builds the production image.

Production deployment is built (ADR 0008). `deploy/` holds the compose project, `install.sh`, `uninstall.sh` and the `updater.sh` loop; `.github/workflows/release.yml` pushes `latest` and `sha-<short>` images to GHCR after CI passes on `main` (docs-only pushes do not release). The panel service has `mem_limit: 384m` (up to 3 live log follows of about 50 MB each; ADR 0008 note). The owner's guide is `docs/deploy.md`.

## Architecture

One Go binary (`cmd/panel`) serves the JSON API and the embedded React app (`web/`, built into `internal/web/dist`). It binds `127.0.0.1` only and is reached through a Cloudflare Tunnel (ADR 0006).

- `internal/config`: reads `PANEL_ADDR` and refuses any address that is not `127.0.0.1:<port>`. It also reads `WORKSPACE_ROOTS` (comma-separated absolute paths, the only folders that may become workspaces) and `PANEL_DATA_DIR` (the panel's own state, default `/data`). Drive settings: `PANEL_SECRET_KEY` (32 bytes, 64 hex or base64; empty is allowed, anything else is a startup error), `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (both or neither) and `PANEL_PUBLIC_URL` (`https://host[:port]`, or `http://localhost[:port]` or `http://127.0.0.1[:port]`; no path, one trailing `/` is dropped). Without a usable set `Config.DriveReason()` names what is missing (a release build needs both Google values) and Drive is `not_configured`. The `dev` build also reads `PANEL_DEV_BACKUP_MIN_FREE` (a raised minimum for the backup disk check; a release build ignores it). `compose.dev.yaml` sets a fixed dev key and `PANEL_PUBLIC_URL=http://localhost:5173`; `deploy/install.sh` generates `PANEL_SECRET_KEY` into a new `panel.env` (appended to an old one without it), and asks for the other three as optional (`docs/google-drive.md`).
- `internal/secret`: `Seal` and `Open` (AES-256-GCM, random nonce, `v1:<base64>`); `ErrBadSeal` for any failed open. Seals the Drive refresh token with `PANEL_SECRET_KEY`.
- `internal/auth`: the `Verifier` seam and the `Require` middleware. Release builds use `AccessVerifier`: it checks the `Cf-Access-Jwt-Assertion` JWT (signature, issuer, audience, expiry) and needs `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`, or startup fails. Setup is in `docs/cloudflare-access.md`. The `dev` build tag swaps in the fixed `dev@localhost` identity; it must never reach a release binary.
- `internal/api`: the router and API types. Only `GET /api/health` is public; everything else goes through `auth.Require`. `GET /api/me` returns the verified email. Workspace flow: `POST /api/scans` (starts a scan, 409 while one runs), `GET /api/scans/{id}`, `GET /api/scans/{id}/events` (per-job SSE: `progress`, then `end`), `POST /api/scans/{id}/track` (stores the workspace and its projects, tracked or ignored, in one transaction), `GET /api/workspaces`, `GET /api/projects` (tracked projects with effective status and allowed `actions`; Unknown when Docker cannot be read). Lifecycle and live state: `POST /api/projects/{id}/{action}` (`start`, `stop`, `restart`; waits for the outcome and answers 200 `ActionResult {outcome, status, message, actions}`; 409 `locked` or `not_allowed` and 503 `docker_down` with `ActionRefused`; 404 for an unknown project), `GET /api/events` (SSE, one `state` event per change, a `LiveState {dockerUp, projects, backups, drive}`: `backups` lists the queued and running backups, `drive` is the full `DriveStatus {state, email, folder, reason}`) and `POST /api/docker/check` (Retry: one fresh Docker read for the hub). Every state-changing `POST /api/*` must send `Content-Type: application/json` or it gets 415 and nothing runs (`requireJSON`, inside `auth.Require`). Field errors are 422 `{error, field, code}`.
  Drive and backups: `GET /api/drive`, `POST /api/drive/connect {returnTo}` (answers `{url}`; a `returnTo` that is not a local path is replaced with `/settings`; 409 `not_configured`), `GET /api/drive/callback` (consumes the single-use state, 302 to the stored `returnTo` plus `drive=connected|declined|error&code=`; an unknown or foreign state is a 400 page), `GET /api/drive/folders`, `POST /api/drive/folder {id | name}` (select or create; 422 `id`/`name`), `POST /api/drive/test` (200 `{ok, code?, message?}`, 409 `busy`) and `POST /api/drive/disconnect` (409 `busy` when a connect landed while it waited: nothing is disconnected, recorded as refused). Drive failures are 502 `{error: code, message}` with the codes `token_expired`, `no_access`, `folder_missing`, `quota` and `unreachable`. `POST /api/projects/{id}/backups {database}` (a `Database.key`; 202 `{id}`; 409 `BackupRefused {error, message, id?, needBytes?, freeBytes?, service?}` with the refusal codes of `internal/backup`, `id` only for `already_running`; 422 `database`; 404; 503 when closed), `GET /api/projects/{id}/backups?limit&before` (history, newest first, 50 by default, 100 at most; active rows come from the manager), `GET /api/backups/{id}`, `POST /api/backups/{id}/retry` and `GET /api/backups/{id}/download` (streamed from Drive through the panel; only for `ok`; the browser opens it as a plain link, so every failure before the first byte is a short HTML page with a link back and its status kept (404 unknown id, 409, 502 with the Drive words); a failure after the first byte cuts the connection, and a client cancel is not logged as a warning). Each `Project` carries `driveFolder`, the Drive sub-folder its backups go to (`backup.ProjectFolder`, the slugged display name). Each project `Database` carries `key` and a server-decided `backup {allowed, reason, service}` (`service` is the resolved compose service, for "Start <service> first"; null on scan rows); the browser never derives it. Dev builds add `GET|POST /api/drive/fake-consent` (the fake Allow/Deny page); a release binary has no such route.
  Workspace management: `POST /api/rescans {workspaceId}` (0 = every workspace; answers 202 `{id}`, 409 `ScanBusy` while a scan runs, 409 with no workspace, 404 for an unknown `workspaceId`), `POST /api/workspaces/{id}/remove` (deletes the workspace and its projects, 200 `{removed}`; 409 while a scan runs or a project is locked or in flight; 404 for an unknown workspace; records `workspace.remove` on every answer after the workspace is found, except a 404 from a concurrent removal) and `POST /api/projects/{id}/untrack` (a present project becomes ignored, a Not found one is deleted; 200 `{removed}`; 409 `ActionRefused` while locked; 404 unknown). `POST /api/scans/{id}/track` also takes a rescan job: it lists only the rows to add, adds them to the existing workspaces (an ignored one is tracked again) and stores the New rows it leaves out as ignored. `ScanJob` and `ScanBusy` carry `rescan` (and `ScanJob.workspaceIds`), `Project` carries `missingSince`.
  Project detail: `Project` also carries `publicDomain`, `stopTemplate` (`stop` or `down`), `alertCpuPercent` and `alertRamMb` (null = server default), `composeFiles`, the live `cpuPercent`, `memBytes` and `upSince`, and `containers` (`Container`: status word, ports, per-container CPU and RAM, restart count, `startedAt`, `exitReason`, `health`; a Not created row per service without a container). `GET /api/projects` reads only `docker ps`, so there the metrics are null and `upSince` is empty; `/api/events` fills them in. `POST /api/projects/{id}/settings` replaces display name, public domain, stop template and both alert thresholds in one call (200 with the `Project`; 422 field errors; 404 unknown; the panel's own project cannot change its template). `GET /api/projects/{id}/logs?service=` is SSE: `lines` events (the first is the backlog) and a final `end {reason, message}`. The end reasons are `exited` (the follow ended, or nothing runs), `slow` (the viewer fell behind), `error` (the backlog or the follow failed; the message is masked) and the refusals; only an unknown id is a plain 404, every other refusal (`unknown_service`, `not_found`, `docker_down`, `too_many_log_streams`) is an `end` reason because `EventSource` cannot read a non-200 body. Every SSE stream (`/api/events`, scan events, logs) sends a `ping` event (`data: {}`) every 25 s (`sseHeartbeat`); a named event, not a comment, so the browser can see it. After an add or a settings change the API calls `Hub.Refresh()`; an untrack and a removal tell the hub through `WithLocks`.
- `internal/runner`: the only package that runs processes. A registry of argv templates keyed by (action, stack): `compose.config`, `compose.up`, `compose.stop`, `compose.restart`, `compose.down`, `compose.logs` (follow, all services), `compose.logs.service` (follow, one service) and `compose.logs.tail` / `compose.logs.tail.service` (the 500-line backlog; each with a `.override` variant), plus `docker.containers`, `docker.inspect`, `docker.stats` and `docker.ping`, and the database actions `db.pg.dump`, `db.mysql.dump`, `db.mongo.dump`, `db.pg|mysql|mongo.size` and `db.dump.stop` (plus `db.pg.dump.default` and `db.pg.size.default`, each with a `.override` variant): `compose exec -T {service} sh -c <fixed script> sh [{dbname}]` (ADR 0011). The scripts (`dbscripts.go`) read the credentials from the container's own environment or its `_FILE` twins, never through the panel, and the only value is the `dbname` slot (`ValidDBName`), used as `"$1"`. The dump scripts run the dumper as a child they `wait` for, record `<shell> <dumper>` pids in `/tmp/.scp-dump.pid` (mktemp, renamed into place with `mv -fT`, so a symlink to a directory is never moved into; a failed claim removes its temp file and the dump runs unrecorded), forward signals to it, and refuse with `a previous dump is still running` while that file names a live dump; `db.dump.stop` (no value, through `Run`, at most about 12 s) TERMs then KILLs only a pid whose `/proc` entry is a live dumper or dump shell (before KILLing a dump shell it TERMs that shell's children, so a shell held in a foreground command runs its trap and removes its credentials file), and removes the file. Placeholders have kinds: a path (absolute, clean), `ids` (1 to 1,000 full 64-hex container ids, one argv element each), `service` (`^[A-Za-z0-9][A-Za-z0-9_.-]{0,62}$`, so never a flag) and `since` (RFC 3339 UTC). Read commands time out after 15 s, lifecycle commands (`compose.up/stop/restart/down`) after 60 s, `docker.ping` after 5 s; each output stream is capped at 4 MiB. `Runner.Stream` is the one call with no timeout: it delivers each masked stdout/stderr line (cut at 16 KiB) until the command exits or its context is cancelled, and it runs only the follow actions, which `Run` refuses (ADR 0010). Every command runs in its own process group and the whole group is SIGKILLed on timeout or cancel, so a `docker compose` plugin child cannot outlive it; the panel containers run with `init: true` to reap the killed trees. Stderr and error messages are masked (`••••`) for the secret values the caller passes. The child gets a minimal environment (`PATH`, `HOME` and `DOCKER_CONFIG` under `$PANEL_DATA_DIR/docker`), never the panel's own. `Runner.RunTo(ctx, s, a, v, secrets, w)` runs the dump actions only (`Run` and `Stream` refuse them): stdout goes straight to `w` with no cap, there is no total timeout but a 5-minute stall limit (`*StallError`, reset by every write) and a 6-hour ceiling (`*TimeoutError`), a write error stops the command and is returned wrapped, and the stderr it returns is masked. The size actions use `Run` (15 s).
- `internal/roots`: the `WORKSPACE_ROOTS` guard. Resolves a path (symlinks, `..`) to one canonical form and refuses anything outside the roots, with the error codes `not_absolute`, `not_found`, `unreadable`, `outside_roots`, `not_a_folder`.
- `internal/store`: SQLite at `$PANEL_DATA_DIR/panel.db` (`modernc.org/sqlite`, no cgo), with embedded migrations applied on open. Holds workspaces, projects and scan jobs; a job left running becomes interrupted on reopen. The `activity` table (migration 0002) is the append-only record of who did what: two inserts (a `running` row, or a finished one such as a refusal), one guarded `running` to final update and a store-level reader `RecentActivity` (no HTTP route yet), never a delete; the actor email comes only from `auth.FromContext`, the reason is masked, and a row left `running` becomes `interrupted` on reopen. Scans, tracks and project actions (refusals included) are recorded. Migration 0003 adds `projects.missing_since` (set when a rescan cannot find a tracked project's folder, cleared when it is found again; NULL means present). Workspace management lives in `internal/store/manage.go`: `RemoveWorkspace`; `UntrackProject` (a tracked project becomes ignored and its databases are deleted; a missing one is deleted); `ApplyRescan` (a refresh clears missing; Found matches by path in any workspace, Missing is scoped to the reporting workspace; only `state='tracked'` rows; `display_name` is never touched); `AddProjects` (adds into existing workspaces, re-tracks ignored rows, writes a "tracked" marker into the job params in the same transaction; `ErrAlreadyTracked`, `ErrAddedMeanwhile`, `ErrWorkspaceGone`). The activity actions are now `scan.start`, `scan.track`, `workspace.rescan`, `workspace.remove`, `project.start|stop|restart`, `project.untrack`, `project.remove` and `project.settings` (email, changed fields with old and new values). Migration 0004 adds `projects.public_domain`, `stop_template` (`stop` default or `down`, CHECKed) and the nullable `alert_cpu_percent` and `alert_ram_mb`; scans and rescans never touch them. `UpdateSettings` (`internal/store/settings.go`) replaces all five settings in one transaction and returns the project before and after. Migration 0006 adds `databases.name_explicit`. Migration 0005 adds `drive` (one row: state, the sealed refresh token, email, folder), `drive_oauth_states` (single-use, 10-minute states with the redirect and the `returnTo` used; expired ones are deleted on every put and take) and `backups` (state `queued|running|ok|failed|refused|interrupted`, the project and database snapshot, `db_key`, `db_service`, file name, Drive file id and link, sizes, the four `steps` as JSON, error, hint, who and when); `store/drive.go` and `store/backups.go` hold them (`ProjectBackups(projectID, before, limit)`, `ActiveBackup`; `UpdateBackup` also stores the worker's resolved `db_service`; `Open` interrupts a queued or running backup, its running steps failed and waiting ones skipped). The activity actions gain `backup.run` (who, which database, the result, the failed step and the reason; a refusal is recorded finished as `refused`), `drive.connect`, `drive.folder` and `drive.disconnect`.
- `internal/project`: the `Status` values (`running`, `partial`, `stopped`, `error`, `unknown`, plus the in-between `starting`, `stopping`, `restarting` and `notfound`) and the mapping from `docker.containers` output. `Allowed` gives the actions a status permits (the server uses it; the UI reads the `actions` the server sends and never derives them), and `AnyActive` says whether anything runs or restarts. The actions `untrack` (offered in every status except in flight and Not found, even with Docker down and for the panel's own project) and `remove` (the only action of `notfound`) are only ever stored as the project's allowed actions; both are served by `POST /api/projects/{id}/untrack`. `project/backup.go`: `DatabaseKey` (`type:location:name`), `ResolveService` (the database's compose service, by service or container name) and `BackupReason`, the database half of the backup rule: `not_supported` (SQLite, a database outside a container, an unresolved service), `no_db_name` (a placeholder name, except PostgreSQL, which uses its default database), `docker_down` (Docker cannot be read, so whether the service runs is not known; "Docker is not responding.") and `db_not_running`, in that order. The scanner keeps a database name from a URL path over a placeholder, and marks a name a variable or URL set `Database.NameExplicit` (migration 0006, `databases.name_explicit`), so `MYSQL_DATABASE: db` on service `db` is not taken for the placeholder; rows stored before it read as placeholders until the next rescan.
- `internal/control`: project lifecycle. The `Controller` holds per-project in-memory locks; `Do` checks (not allowed, locked, Docker down, the panel's own project; a refusal is a `*Refusal` error, answered 409 or 503 and recorded in `activity` as `refused`), runs the command with the project's `.env` secrets masked, re-reads Docker and settles an `Outcome` (`ok`, `failed`, `timed_out`). A start or restart that exits 0 but leaves anything but Running or Partial is failed (Partial counts as started); a stop that exits 0 but leaves something running or restarting is failed. The command runs on its own context, so a client disconnect never aborts it, and the lock is released on every path. The `Hub` does one non-overlapping Docker read every 5 s, shared by all `/api/events` subscribers and only while someone is subscribed; a generation counter drops a stale read that lands after a lock change, and `Check` backs Retry. Lock order: `hub.mu` then `ctl.mu`. `Views` decides a row in this order: in flight, then a missing project as `notfound`, then Docker; a project held for a store write keeps that computed status but has no actions. `Do` re-verifies the project after taking the lock, so no command runs on a project untracked meanwhile. `Untrack` holds the project's lock for the store write and records `project.untrack` (or `project.remove` for a missing project). `WithLocks` holds several projects' locks for a write (used by `Untrack` and workspace removal); after a successful write it calls the observer's `storeChanged` while the locks are still held (the hub bumps `tsGen`, so a tick that read the store before the write publishes nothing), then releases with `lockChanged` as on every path; it never calls the hub with `ctl.mu` held, and its callers need no `Hub.Refresh`. The tick runs `docker.inspect` (restart count, start time, health, exit reason) for the tracked, present projects' containers right after `docker ps`, and a separate non-overlapping metrics read (`docker.stats`) starts every 10 s (start to start) while someone subscribes and is skipped while the last tick found Docker down; failed or skipped metrics reads keep the last values for 30 s, then they go null. Inspect and metrics are maps keyed by container id and survive `lockChanged`. `Hub.Containers(ctx)` is `Check` plus the container list (ok false when Docker is down) for the log streams. A stop on a project with the `down` template runs `compose.down` (containers and networks removed, volumes kept; it then reads Stopped), and the panel's own project always stops with `stop`. `ProjectView.DatabaseViews` gives each database its `Key` and `Backup {Allowed, Reason, Service}`: `not_found` for a missing project, then the database reason, then the Drive reason (`drive_not_connected`, `drive_expired`, `folder_missing`). `State` carries `Backups` and `Drive`, read from sources set with `SetBackupSource` and `SetDriveSource` under `hub.mu` (lock order hub.mu, then the manager's or Drive's own lock); `Hub.Publish()` sends the state from the cache with no Docker or store read (it is the `OnChange` of the backup manager and the Drive service), and `Hub.RecentContainers(ctx, maxAge)` serves the backup manager's running check from the cache. `Hub.Refresh` asks for a fresh read and always bumps `tsGen` (so a tick that read the store earlier publishes nothing); then, with no loop running it invalidates the cache, with a tick running it does nothing more (that tick drops its list and ticks again), otherwise it starts a detached tick. `cacheTS` is the `tsGen` the cached list was read under: while it is behind, nothing publishes from the cache (`Publish`, the metrics merge, `lockChanged`, a `Subscribe` reusing it), and a `lockChanged` starts a catch-up tick instead when none runs. A tick that cannot read the store while `cacheTS` is behind keeps only its Docker half (so `Check` still answers Retry), publishes nothing and returns stale, so its runner ticks again (`maxTickReads` in all). `Publish` and the metrics merge also wait while `cacheGen` is behind the Controller (only between a lock change and its `lockChanged`, a store call long; a lifecycle command's take syncs it before the command runs, so backup progress keeps flowing during it). `Subscribe` starts the tick loop after its own tick, and the loop's first tick comes `tickInterval` after the last read, so one subscribe from cold reads Docker once.
- `internal/scan`: the workspace scanner. It walks depth 1-3 (symlinks, hidden folders and `node_modules` skipped; no descent into a project), reads each compose file with `docker compose config --format json --no-env-resolution` through the runner, parses `.env` for masking and database hints, detects databases without keeping any secret, and recognises the panel's own project (Monitor only) by its image label. It runs one scan at a time and fans progress out through a broadcaster. A rescan is a `scan` job with params `{"depth":0,"rescan":[workspace ids]}`; each workspace is scanned at its own depth, and the `Guard` (set with `SetGuard`, the `WORKSPACE_ROOTS` check) is run by the Manager. A workspace is skipped with a warning when the Guard refuses it or it resolves to a different canonical path, when its root is missing or unreadable, or when it lists no compose folder while it has tracked projects: nothing is marked missing and its `last_scan_at` is kept. A project refreshes only from what was read (config and containers), so a failed `compose config` keeps the stored services and Docker down keeps the panel's own `self` flag. A new path under two nested workspaces belongs to the deepest scanned root. `OnChange` calls `Hub.Refresh` after the apply, and `WhileIdle(fn)` runs `fn` only while no scan runs (workspace removal uses it).
- `internal/logs`: live container logs for `GET /api/projects/{id}/logs`. One shared stream per (project, service or all): the first viewer runs the backlog (`compose logs --tail 500`, through `Run`), sorts it by timestamp, then starts one `--follow --since <start>` through `Runner.Stream` only if a container of the selection is running or restarting (else it sends the backlog and ends `exited`); follow lines already in the backlog are dropped, so the hand-off has no gap or duplicate. Lines are parsed (ANSI stripped, compose status lines dropped, the prefix mapped to a container through `Hub.Containers`) and masked with the project's `.env` values. A stream keeps a 500-line ring for late viewers, sends batches at most every 200 ms, ends a viewer that falls 16 batches behind (`slow`) and cancels its follow process the moment the last viewer leaves. A panic in the follow's line callback (which runs on exec's copy goroutine) is recovered and ends the stream `error`, freeing the key. At most 3 follows run panel-wide (a joiner of an existing stream always gets in); a fourth is refused as `too_many_log_streams`. Reading logs is not recorded in `activity`.
- `internal/drive`: Google Drive behind two seams. `Client` (`AuthURL`, `Exchange`, `Session(refresh)`) and `Session` (`Account`, `ListFolders`, `CreateFolder`, `FindOrCreateFolder`, `Upload`, `Download`, `Delete`, `Revoke`). `NewGoogle` is the real client (scope `drive.file` only, offline access with forced consent, resumable uploads in 8 MiB chunks with up to 3 resumes per chunk and a 2-minute stall watchdog; the account email comes from `about.get`); `NewFake(dir, publicURL)` keeps files under `<dir>/<folderId>/<name>` for tests and dev. `NewClient(cfg, dataDir)` (build tags) returns the fake under `$PANEL_DATA_DIR/fake-drive` in a `dev` build with no `GOOGLE_CLIENT_ID`, and always Google in a release build. Errors are `*Error{Code}` (`token_expired`, `no_access`, `folder_missing`, `quota`, `unreachable`; `Words(code)` gives the user's sentence, and `token_expired` adds that a Google Cloud app in Testing expires tokens after 7 days); they never hold a body, URL or token. `Service` is the connection: `Status()` reads a cache (never the store or network), `OnChange(fn)` fires after a change, a token that cannot be opened marks the connection `expired`, and any `token_expired` from a session flips it (a generation counter keeps an old session from flipping a new connection). `StartConnect` and `FinishConnect(actor, state, code, errParam)` (the state is single-use, bound to the actor and stored with its redirect; the stored redirect is the one `Exchange` uses; a reconnect with the same account keeps the folder), `Folders`, `SelectFolder` (only a folder the panel listed), `CreateFolder` (finds an existing one of that name), `Test` (uploads and deletes a tiny file) and `Disconnect` (reads and deletes the row under the write lock, then revokes the old token, best effort; a connect that landed after Disconnect was called is left as it is and Disconnect answers `ErrConnectedMeanwhile`). A failed `FinishConnect` is logged (code and the sanitised error only), and `ConnectWords(code)` words it: `no_access` there is Google refusing the app (client id, secret or redirect URI), not a folder. A fresh token that could not be stored (account read, seal or store write failed) is revoked, best effort. The panel's redirect URI is `<PANEL_PUBLIC_URL>/api/drive/callback`.
- `internal/backup`: manual database backups. `Manager.Enqueue(ctx, t store.Tracked, dbKey, actor)` runs the checks in order: project present (`not_found`), database still detected (`unknown_database`) and the location (`not_supported`: SQLite or a database outside a container); these three write nothing. Then an active backup of that database (`already_running` with its id and no row; checked before Drive, so a second press answers it even while Drive is expired or disconnected), Drive (`drive_not_connected`, `drive_expired`, `folder_missing`), the per-database reservation (`already_running` again for one queued meanwhile; concurrent presses wait for the holder and get its outcome), the service and name (`no_db_name`, worded per type: `POSTGRES_DB` for PostgreSQL, `MYSQL_DATABASE` or `MONGO_INITDB_DATABASE` otherwise; `docker_down`; `db_not_running`) and the disk rule (`disk_short`: the `db.*.size` read, need = half the data size + 100 MiB, 500 MiB when the size cannot be read, free space from `statfs` on `$PANEL_DATA_DIR/tmp`, `Bavail` × `Frsize`; a failed free-space read does not block). A refusal at the Drive, service or disk check is stored as a `refused` row with all steps skipped and recorded in `activity`. One worker runs one backup at a time in order: it re-checks (re-reading the project from the store: one untracked, removed or missing meanwhile is `not_found`, a database no longer detected `unknown_database`, otherwise it runs with the project as it is now), then Dump (`RunTo`, gzip level 1, to `$PANEL_DATA_DIR/tmp/backup-<id>.gz`, mode 0600), Compress, Upload (the slugged project name as a sub-folder, found or created) and Prune (always skipped: no retention yet). The file is `<project>_<db>_<YYYYMMDD-HHmm>.sql.gz` (`.archive.gz` for MongoDB, in the panel's `TZ`). Whenever Dump ends without the dump exiting by itself (stall, ceiling, failed write, cancel or `Close`, a client that did not run, a panic in `RunTo`), the worker runs `db.dump.stop` best effort on `context.WithoutCancel` bounded at 15 s (`stopWait`), logging a Warn on failure; the stall and ceiling words then say the dump "was stopped" instead of "may still be running". A dump failure shows the last non-warning stderr line plus a hint from a fixed table (`hints.go`, naming a variable, never a value; the script's `a previous dump is still running` gets "A previous backup of this database is still finishing inside the container; try again in a few minutes."; a `mariadb` image gets the `MARIADB_*` words and `mariadb-dump`, an image that is neither names both families); the exit code, not stderr, decides success. A failure removes the temp file and never touches Drive. A failure to read the temp file during the upload (a short file included) is the panel's own: "Could not read the dump file: …", masked, not logged as a Drive outage. A failed close of the compressor or the temp file fails Compress (the dump had exited 0). Drive's link is stored only when it is `https` on `drive.google.com` or `docs.google.com`, or on the `PANEL_PUBLIC_URL` origin (the fake), else empty (`drive.Service.SafeLink`), since the UI renders it as an href. A worker panic fails the step; `Start` removes leftover temp files and `Close` interrupts the running and queued backups. A backup that ends interrupted before its activity started (the worker stopped during its re-check, or a queued one drained at `Close`, including one queued while `Close` ran) records one finished `backup.run` with result `interrupted`. Progress is published at most every 500 ms and never stored. `Retry(ctx, id, actor)` re-runs a failed, refused or interrupted backup from the first step (`not_retryable` otherwise).
- `deploy/`: the shell scripts and `compose.yaml` that install, update and uninstall the panel on a server, with their tests in `deploy/test/`. Run on Linux only; test them through `make deploy-test`. `docs/google-drive.md` is the owner's guide for the Google Cloud setup (a published app, the redirect URI, the three variables).
- `internal/web`: serves the embedded single-page app for every non-API path.
- `web/`: React, Vite and TypeScript. Pages are declared in `web/src/app/routes.ts`. Built: `/onboarding` (path and depth, live scan progress, results table, Add), the `/` Dashboard table of tracked projects with lifecycle controls, and the Workspaces card on `/settings`. The app runs in a data router (`createBrowserRouter`, `routeObjects` in `web/src/app/App.tsx`, so a page can block navigation). `LiveProvider` (`web/src/app/live.tsx`) wraps the shell (`AppShell`) and holds one `EventSource` on `/api/events` for every page; it shows the Docker banner (Retry posts `/api/docker/check`) and the connection state: `ConnectionBadge` (top right of the content area) reads Realtime, "Connection lost, retrying…" (the page dims to 55 %) or, when `/api/me` shows the Access session ended, "Session expired" with Reload. A 60 s watchdog per source (`armWatchdog`, `STALE_MS`), re-armed on every `state` and `ping`, catches a half-open connection: it shows Connection lost and reopens the source after 1 s, without counting it as a closed attempt; `useLogStream` does the same on `lines` and `ping`, keeping its lines. `StatusBadge` is the status pill for all nine statuses. The Dashboard row has a Start/Stop switch and a ⋯ menu (Start, Restart); Stop and Restart of a Running or Partial project ask first in a confirm dialog; results show in a toast stack. The row's allowed actions come from the server, never re-derived in the browser. The project name links to `/projects/:id`, and the table has live CPU and RAM columns. `web/src/lib/useProjectActions.tsx` holds the action flow (confirm, run, toast) shared by the Dashboard and the detail header. `/` redirects to `/onboarding` when there is no workspace (first-screen rule; #26 setup steps are not built). The Dashboard header has a Rescan button; a Not found row shows "Folder missing since the <HH:MM> scan. Not removed automatically." and its ⋯ menu offers Stop tracking (ask first, toast "Stopped tracking <name>") or, for a Not found row, Remove from list. Both are red, per #72, which is a recorded drift from design 10's neutral Remove button. `/rescan/:id` (`RescanPage`, `RescanResults`) shows live rescan progress, then the New rows (tagged New), a "Show ignored (N)" toggle where an ignored project can be checked and tracked again, and warnings that stay; a rescan with nothing new ends "Rescan finished: no new projects, Y not found". `/onboarding` also accepts router state `{scanId}` to attach to a running first scan, and `/rescan/:id` on a first-scan job redirects there. The Settings Workspaces card has Rescan and Remove per workspace; `web/src/lib/useRescan.ts` is the shared start-or-attach hook for the Dashboard and Settings. `/projects/:id` (`ProjectPage` with `projectContext`) is the detail page: header (name, status, containers, path, domain, uptime, actions) and four tab routes that live in the URL: Overview (index: CPU/RAM, containers table, a failed-components panel whose View logs opens Logs on that container's most recent error), `/logs` (`ProjectLogs`, `useLogStream`: service filter, level words, 2,000 lines held, Download, reopens when a container runs again), `/database` (detected databases, each with Back up now and, while one runs, its compact progress; a Backup history table with Download, Open in Drive, Retry and Show older; a Backup schedule empty state) and `/settings` (`ProjectSettings`: name, public domain, stop template, alert thresholds stored but not sent, Stop tracking; unsaved changes ask before navigating away). The Settings Google Drive card (`DriveCard`) covers the Drive states (not set up, not connected, expired, connected with folder, Test connection and Disconnect); `DriveReturn` turns `?drive=…` into a toast. Back up now is one flow, `web/src/lib/useBackup.tsx`, shared by the header, each database, the Dashboard ⋯ menu and the `?backup=<key>` return: it opens the chooser, the "Connect Google Drive first" dialog or the closable progress dialog, which follows `useLive().backups`. Whether a button is enabled comes from `Database.backup`. `/backups` (`BackupsPage`) is minimal: the Drive banners and the running or waiting backups; the all-backups table (#57) is not built. The other pages are placeholders for later issues.
